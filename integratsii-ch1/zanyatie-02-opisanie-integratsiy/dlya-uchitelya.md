## 1. Контракт (5–15 мин)

«Вопрос: что такое контракт между двумя системами? Не из учебника, своими словами.»

[Она говорит. Например: «договор, что кто что отдаёт».]

«Именно. Давай точнее:

**Контракт интеграции — это точное описание: что одна система посылает другой, в каком виде, что получит в ответ, и что будет, если что-то пошло не так.**

Почему он "закон":
- по нему работают **две стороны независимо**. Я меняю свою реализацию — пока контракт не сломан, вторую сторону это не трогает.
- на собесе: «как вы описываете API?» Ответ «табличка в Confluence с названиями полей» = красный флаг.

**7 частей контракта:**
1. Эндпоинты (метод + путь)
2. Формат запроса: заголовки, query params, body
3. Формат ответа: тело, статусы
4. Схемы данных (типы, обязательность, ограничения)
5. Ошибки: какие, какого вида
6. Версия
7. Аутентификация (тип, не сами ключи)

Вопрос: чем контракт отличается от спецификации?»

[Ожидаю: «спецификация шире, в неё могут входить бизнес-правила; контракт — только граница обмена». Если не говорит — подсказываю: «в контракте есть бизнес-правило "если заказ на сумму > 100 000 нужен менеджер"?»]

## 2. Структура эндпоинта (15–30 мин)

«На каждый эндпоинт описываем:

```
POST /api/v1/orders
Headers:
  Authorization: Bearer {token}
  Content-Type: application/json
Query:
  (нет)
Body: CreateOrderRequest (схема ниже)
Responses:
  201 -> Order (Location: /api/v1/orders/{orderId})
  400 -> Error (валидация полей)
  401 -> Error (нет токена / истёк)
  404 -> Error (товара не существует)
  409 -> Error (товара нет в наличии)
  422 -> Error (семантика: дата доставки в прошлом)
  500 -> Error (ошибка сервера)
```

**Нейминг URI — правила:**
- множественное число: `/orders`, не `/order`
- строчные, дефисы: `/payment-methods`, не `/PaymentMethods`
- вложенные ресурсы: `GET /orders/123/payments`
- **действия не в имени**, если есть REST-метод: `POST /orders`, не `POST /createOrder`

**Исключение:** sub-action — действие, которое не является CRUD по ресурсу:
```
POST /orders/123/cancel    (ок — "отмена" это не PUT/DELETE)
POST /orders/123/pay       (ок — "оплата" это под-действие заказа)
```

Вопрос: почему `POST /createOrder` — плохой стиль? А когда допустимо `POST /orders/123/cancel`?»

[Ожидаю: «REST — ресурс + метод, "create" дублирует POST. Cancel — не CRUD, это действие над состоянием». Если не говорит — объясняю: «POST /orders уже значит "создать". POST /createOrder — тавтология. А cancel — это смена состояния, не CRUD, поэтому sub-action допустим».]

## 3. Схемы данных (30–45 мин)

«Для каждого объекта — таблица полей. Пример: `CreateOrderRequest`:

| Поле | Тип | Обязательное | Ограничения | Описание |
|---|---|---|---|---|
| userId | integer | да | > 0 | Кто разместил |
| items | array[OrderItem] | да | 1..100 элементов | Позиции заказа |
| items[].sku | string | да | min 3, max 32 | Артикул |
| items[].qty | integer | да | 1..999 | Количество |
| total | integer | да | > 0, **в копейках** | Сумма заказа |
| deliveryDate | string | нет | ISO 8601: `YYYY-MM-DD` | Дата доставки |
| comment | string | нет | max 500 символов | Комментарий |
| promoCode | string | нет | max 20 символов | Промокод |

**Грабли (разбираем по одной):**

**Грабли 1: деньги.**
Вопрос: какой тип для суммы заказа — `double`, `float` или `integer`?»

[Ожидаю: integer. Если говорит double —:]

«Почему не double: `0.1 + 0.2 = 0.30000000000000004` в float. Деньги **только integer в минимальной единице**: копейки (RUB) или центы (USD). `total: 500000` = 5 000 00 руб.»

**Грабли 2: даты.**
Вопрос: какой формат для даты доставки — `"01.02.2026"`, `"2026-02-01"`, `1738368000`?»

[Ожидаю: ISO 8601. Если говорит "01.02.2026" —:]

«ISO 8601: `2026-02-01` (date) или `2026-02-01T10:00:00Z` (datetime с таймзоной). Не `"01.02.2026"` — неясно, день/месяц. Не unix timestamp — нечитаемый человеком. Разделяем `date` (только дата) и `datetime` (дата + время).»

**Грабли 3: "может быть пусто".**
Вопрос: поле `comment` — необязательное. Что придёт, если пользователь не заполнил: `null`, `""` (пустая строка), или поля не будет?»

[Ожидаю: выбрать и зафиксировать. Если не говорит —:]

«Выбираем **один** вариант и пишем в схему. Я рекомендую: поле отсутствует (не `null`). Потому что `null` и `""` — разные вещи, и потребитель будет гадать. В JSON: если `comment` нет — не заполнен. Если `comment: ""` — заполнили, но убрали текст.»

**Грабли 4: enum.**
Вопрос: поле `status` в ответе `Order`. Какие значения?»

[Ожидаю: перечислить. Если говорит "какие-то статусы" —:]

«**Перечисляем все значения:** `CREATED`, `PAID`, `SHIPPED`, `DELIVERED`, `CANCELLED`. Потребитель не может гадать, что придёт. Если добавим новый статус — это non-breaking (поговорим про версионирование).»

**Грабли 5: массивы.**
Вопрос: `items` — сколько позиций максимум в заказе?»

[Ожидаю: ограничение. Если не говорит —:]

«Пишем: `minItems: 1, maxItems: 100`. Без ограничения потребитель не знает, на что рассчитывать.»

## 4. Ошибки (45–58 мин)

«**Ошибка — это ответ, не исключение.** В контракте описываем как ответ.

**Единая структура ошибки** (для всех эндпоинтов):

```json
{
  "errorCode": "ITEM_NOT_FOUND",
  "message": "Товар SKU-42 не найден в каталоге",
  "details": {
    "field": "items[0].sku",
    "value": "SKU-42"
  }
}
```

- `errorCode` — **машинный** код. По нему другая система ветвит логику: `if (errorCode == "ITEM_NOT_FOUND") { показать "товар удалён" }`
- `message` — **человекочитаемое**. Показываем пользователю или логгируем.
- `details` — опционально, конкретика (какое поле, какое значение)

**Словарь error-кодов** для эндпоинта `POST /orders`:

| errorCode | HTTP | Когда |
|---|---|---|
| VALIDATION_ERROR | 400 | Нет обязательного поля / битый формат |
| AUTH_REQUIRED | 401 | Нет токена / истёк |
| ACCESS_DENIED | 403 | Токен есть, но прав нет |
| ITEM_NOT_FOUND | 404 | SKU не существует в каталоге |
| INSUFFICIENT_STOCK | 409 | Товара нет в нужном количестве |
| DUPLICATE_ORDER | 409 | Заказ с таким idempotencyKey уже создан |
| INVALID_DELIVERY_DATE | 422 | Дата доставки в прошлом |

**Статусы — повторить (из ч.1, но в контексте ошибок):**

| Код | Смысл | Пример |
|---|---|---|
| 400 | Битый запрос | Нет поля `userId`, `qty: -1` |
| 401 | Нет данных для входа | Нет заголовка `Authorization` |
| 403 | Есть данные, нет прав | Токен есть, но роль `viewer`, а нужно `writer` |
| 404 | Ресурс не существует | `GET /orders/999` — такого заказа нет |
| 409 | Запрос валидный, состояние не позволяет | Заказ уже оплачен, повторно опłacать нельзя |
| 422 | Синтаксис ок, семантика нет | `deliveryDate: 2020-01-01` (в прошлом) |
| 500 | Ошибка сервера | Нечего показывать клиенту, алерт разработчику |

**Вопрос: чем 409 отличается от 400?**»

[Ожидаю: «400 — битый запрос (валидация полей), 409 — запрос валидный, но состояние не позволяет». Если не говорит —:]

«400: ты прислал мусор (`qty: -1`, нет `userId`). 409: ты прислал нормально, но **состояние системы** не даёт. Заказ уже оплачен → нельзя повторно оплатить. Товара 5 шт, а ты просишь 10 → не хватает. Это разные вещи: 400 — чини запрос, 409 — подожди или измени состояние.»

**Вопрос: 401 vs 403?**»

[Ожидаю: «401 — нет токена, 403 — токен есть, но прав нет». Если путает —:]

«401: "предъявите пропуск" (нет `Authorization` header). 403: "пропуск есть, но в этот кабинет нельзя" (токен есть, роль не та).»

## 5. Версионирование (58–70 мин)

«Контракт меняется. Клиенты (другие системы) не могут одновременно "переезжать". Нужна совместимость.

**3 стратегии версионирования:**

| Стратегия | Пример | Плюсы | Минусы |
|---|---|---|---|
| URL | `/api/v1/orders`, `/api/v2/orders` | Просто, видно в логах | Двойная поддержка, урлы грязные |
| Заголовок | `Accept: application/vnd.mycompany.v2+json` | Чистые URL | Сложнее для клиентов |
| Query | `?version=2` | Просто | Не REST-философия |

Обычно: **URL-версия**. `/api/v1/`, `/api/v2/`.

**Breaking vs non-breaking — главное:**

| Изменение | Breaking? | Почему |
|---|---|---|
| Добавить необязательное поле `priceVat` | Нет | Старый клиент просто не увидит новое поле |
| Новый эндпоинт `GET /orders/{id}/history` | Нет | Старый клиент не знает о нём, не сломается |
| Добавить значение в enum `status`: `PARTIALLY_REFUNDED` | Нет (с предупреждением) | Старый клиент должен уметь обработать "неизвестный статус" |
| **Переименовать** `price` → `amount` | **ДА** | Старый клиент будет искать `price`, не найдёт |
| **Удалить** поле `discount` | **ДА** | Старый клиент ждёт это поле |
| **Изменить тип** `total`: integer → string | **ДА** | Старый клиент парсит как число |
| **Убрать** значение из enum | **ДА** | Старый клиент ветвит по этому значению |
| Изменить семантику `409` → теперь `400` | **ДА** | Старый клиент ветвит по статусу |

**Правила:**
- **Добавлять** — можно (non-breaking)
- **Удалять/переименовать/менять тип** — только в новой версии
- enum: добавлять — можно (предупредить), убирать — breaking
- v1 и v2 живут **параллельно** 3–6 месяцев, затем v1 деградируется

**Вопрос: клиент ждёт поле `price` (integer). Мы добавили `priceVat` (integer). Breaking?**»

[Ожидаю: нет.]

«Верно. Старый клиент читает `price`, `priceVat` просто игнорирует. Non-breaking.

**А если переименовать `price` → `amount`?**»

[Ожидаю: breaking.]

«Да. Старый клиент ищет `price`, не находит → падает или показывает 0. Это breaking, нужна v2.

**А если убрать значение `REFUNDED` из enum `status`?**»

[Ожидаю: breaking.]

«Да. Старый клиент имеет ветку `if (status == "REFUNDED")`. Убрали → ветка мёртвая, но код сломан. Breaking.»

**Как деградировать v1:**
1. Заголовок `Deprecation: true` в ответах v1
2. Заголовок `Sunset: Sat, 01 Mar 2027 00:00:00 GMT` (когда v1 умрёт)
3. Логирование: кто ещё использует v1
4. Уведомление клиентам (email/чат) за 3 месяца
5. В день Sunset — v1 возвращает `410 Gone`»

## 6. OpenAPI (70–80 мин)

«**OpenAPI** (бывш. Swagger) — машиночитаемый формат описания REST API. YAML или JSON.

Зачем аналитику:
- **единый источник правды**: из одного файла генерируется документация, mock-сервер, клиентский код, контракт-тесты
- **валидация**: автоматически проверить, что запрос/ответ соответствует схеме
- **собес**: «описываю в OpenAPI 3.x, генерирую доки и моки, валидация через schema»

Минимальный OpenAPI-файл (YAML):

```yaml
openapi: 3.0.3
info:
  title: Orders API
  version: 1.0.0
  description: API сервиса заказов

servers:
  - url: https://api.example.com/api/v1

security:
  - bearerAuth: []

paths:
  /orders:
    post:
      summary: Создать заказ
      operationId: createOrder
      requestBody:
        required: true
        content:
          application/json:
            schema:
              $ref: '#/components/schemas/CreateOrderRequest'
      responses:
        '201':
          description: Заказ создан
          headers:
            Location:
              schema:
                type: string
          content:
            application/json:
              schema:
                $ref: '#/components/schemas/Order'
        '400':
          description: Ошибка валидации
          content:
            application/json:
              schema:
                $ref: '#/components/schemas/Error'
        '401':
          description: Нет токена
          content:
            application/json:
              schema:
                $ref: '#/components/schemas/Error'
        '409':
          description: Нет в наличии
          content:
            application/json:
              schema:
                $ref: '#/components/schemas/Error'
        '500':
          description: Ошибка сервера
          content:
            application/json:
              schema:
                $ref: '#/components/schemas/Error'

  /orders/{orderId}:
    get:
      summary: Получить заказ
      parameters:
        - name: orderId
          in: path
          required: true
          schema:
            type: integer
      responses:
        '200':
          description: Заказ
          content:
            application/json:
              schema:
                $ref: '#/components/schemas/Order'
        '404':
          description: Не найден
          content:
            application/json:
              schema:
                $ref: '#/components/schemas/Error'

components:
  securitySchemes:
    bearerAuth:
      type: http
      scheme: bearer
      bearerFormat: JWT

  schemas:
    CreateOrderRequest:
      type: object
      required: [userId, items, total]
      properties:
        userId:
          type: integer
          minimum: 1
        items:
          type: array
          minItems: 1
          maxItems: 100
          items:
            $ref: '#/components/schemas/OrderItem'
        total:
          type: integer
          minimum: 1
          description: Сумма в копейках
        deliveryDate:
          type: string
          format: date
          description: ISO 8601

    OrderItem:
      type: object
      required: [sku, qty]
      properties:
        sku:
          type: string
          minLength: 3
          maxLength: 32
        qty:
          type: integer
          minimum: 1
          maximum: 999

    Order:
      type: object
      required: [orderId, status, createdAt, total]
      properties:
        orderId:
          type: integer
        status:
          type: string
          enum: [CREATED, PAID, SHIPPED, DELIVERED, CANCELLED]
        total:
          type: integer
        createdAt:
          type: string
          format: date-time

    Error:
      type: object
      required: [errorCode, message]
      properties:
        errorCode:
          type: string
        message:
          type: string
        details:
          type: object
```

**Что из OpenAPI генерируется:**
- Документация (Swagger UI — интерактивная страница)
- Mock-сервер (для фронтенда, пока бэкенд не готов)
- Клиентский код (Java/Python/JS)
- Контракт-тесты (Pact)
- Импорт в Postman

**Вопрос: что из этого можно сгенерировать автоматически из одного OpenAPI-файла?**»

[Ожидаю: доки, моки, клиенты, тесты. Если не говорит — перечисляю.]

**Безопасность в OpenAPI:**
```yaml
securitySchemes:
  bearerAuth:
    type: http
    scheme: bearer
    bearerFormat: JWT
  apiKeyAuth:
    type: apiKey
    in: header
    name: X-Api-Key
  oauth2:
    type: oauth2
    flows:
      clientCredentials:
        tokenUrl: https://auth.example.com/oauth/token
```

API key vs Bearer:
- API key: один ключ на всё, нет срока жизни, сложно отозвать
- Bearer (JWT): срок жизни (1 час), refresh, можно отозвать, разные права по ролям

**Секреты (ключи, токены) — никогда в ТЗ и в OpenAPI.** Только способ получения: Vault, env vars, secrets manager.

## 8. Чек-лист + ДЗ (88–90 мин)

«Чек-лист "контракт готов к передаче разработчику":

- [ ] Для каждого эндпоинта: метод, путь, описание
