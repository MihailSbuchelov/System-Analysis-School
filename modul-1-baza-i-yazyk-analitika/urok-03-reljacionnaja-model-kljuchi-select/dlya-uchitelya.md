## 1. Цели урока

После урока ученик умеет:

- объяснить базовые термины реляционной модели: отношение (таблица), кортеж (строка), атрибут (колонка);
- объяснить назначение и свойства PRIMARY KEY;
- объяснить назначение FOREIGN KEY и смысл связей 1:N и M:N;
- строить схему связей простой предметной области (пользователь–заказ, заказ–товар);
- применять ограничения UNIQUE и NOT NULL и понимать, зачем они нужны;
- писать базовые SELECT-запросы: выбор колонок, WHERE, ORDER BY, LIMIT, псевдонимы (AS);
- читать чужой SQL и объяснять его «человеческими словами».

**Не цель урока:** писать INSERT/UPDATE/DELETE, сложные JOIN, агрегации (COUNT, GROUP BY), проектировать нормальные формы. Это будет в уроках 4–5.

## 4. Сценарий по шагам

### 4.1. Вступление (3–5 мин)
Связать с курсом: «В уроке 2 мы научились просить данные у сервера через REST. Сегодня заглянем внутрь — как эти данные лежат в базе и как их доставать с помощью SQL». Объявить, что к концу урока ученик сам напишет 7–8 SELECT-запросов.

### 4.2. Реляционная модель (слайд 3)
Определение:

> Реляционная модель — хранение данных в таблицах, между которыми есть связи.

Разобрать три термина на аналогии «анкеты»: таблица = анкета, строка = заполненная анкета одного человека, колонка = поле анкеты. Опираться на урок 1, где таблица `users` уже была видна. Спросить: «что удобно хранить в таблицах?» — ответ: «однотипные сущности: пользователи, товары, заказы».

Акцент для будущего аналитика: термины «кортеж/атрибут/отношение» он встретит в документации и в разговоре с разработчиками — уметь переводить их на «строки/колонки/таблицы» очень пригодится.

### 4.3. Таблица и её правила (слайд 4)
Показать таблицу `users`. Подчеркнуть: строка = один объект мира (один пользователь), колонка = одно свойство (email). Правило: строки в таблице не повторяются — почему? философски: «два одинаковых пользователя — это всё же разные люди, а номер строки у каждого должен быть свой». Это подводит к PK.

### 4.4. PRIMARY KEY (слайд 5)
Проговорить свойства и главное для аналитика: «уникальный идентификатор сущности» — так это звучит в требованиях. Разобрать, почему `email` плохой PK: меняется и может совпадать у людей; id — искусственный и неизменный. Показать, что именно по PK будем искать одну строку.

### 4.5. FOREIGN KEY (слайд 6)
Разобрать таблицу `orders` и колонку `user_id`. Объяснить буквальное слово: «внешний ключ» — «чужой» первичный ключ, ссылка в другую таблицу. Аналогия: «в заявке на отпуск стоит табельный номер сотрудника — это и есть внешний ключ, он ссылается на таблицу сотрудников».

Акцент: FK — это то, как база следит за **целостностью** («нельзя заказать у несуществующего пользователя»). Вопрос-якорь: «куда мы пойдём, чтобы узнать имя владельца заказа?» — «в таблицу users по user_id». Именно так готовится почва для JOIN в уроке 4.

### 4.6. Связи 1:N и M:N (слайды 7–8)
Связь 1:N: пользователь—заказы, «сторона один» — пользователи, «сторона многие» — заказы; FK лежит на стороне «многих» (в `orders.user_id`). Проговорить: «если бы FK лежал в users, один пользователь — один заказ, а нам нужно много».

Связь M:N на примере заказ—товар: в строке заказа нельзя записать список товаров, в строке товара нельзя записать список заказов → нужна промежуточная таблица `order_items`. Связать с реальностью: в чеке магазина есть позиции «2 × молоко» — это и есть строки `order_items` (order_id, product_id, quantity).

### 4.7. UNIQUE и NOT NULL (слайд 9)
Показать CREATE TABLE и разобрать три ограничения. Спросить: «а какие ещё поля, кроме email, стоит сделать UNIQUE?» (ИНН, артикул товара). Подчеркнуть: ограничения — это «правила, которые база держит сама», аналитику их надо прописывать в требованиях.

### 4.8. Учебная БД и SELECT (слайды 10–12)
Показать полную схему «магазина» (mermaid), затем поочерёдно: SELECT без условий → WHERE → ORDER BY + LIMIT. Проговаривать каждый пример вслух и просить ученика «перевести» запрос на русский:
- «SELECT name, price FROM products WHERE price < 100000 » → «дай названия и цены товаров дешевле 100 тысяч».

Таблица операторов WHERE (равно, LIKE, IN) — прогнать каждый на примере.

### 4.9. Псевдонимы (слайд 13)
Показать `AS`. Важно: псевдонимы — это «подписи для человека», таблицу они не меняют. Акцент: отчёты, которые собирает аналитик, часто нужно показывать с понятными названиями колонок.

### 4.10. Разбор запроса целиком (слайд 14)
Прогнать sequence-диаграмму «аналитик → БД» со всеми шагами: фильтр → сортировка → лимит. Правило-шпаргалка: сначала строки по условию, потом порядок, потом «сколько взять».

### 4.11. Практики 1–3 (30 мин суммарно)
- П1 (10 мин): базовые запросы, учитель помогает с первым.
- П2 (15 мин): посложнее (LIKE, IN, сортировки).
- П3 (10 мин): «перевести» запрос на человеческий язык, назвать PK/FK в нём. Это самое аналитическое задание — подчеркнуть это!

Во время практики ходить по экранам, поправлять синтаксис (пропущенные кавычки, `price < 50 000` с пробелом из-за пробелов — заметить, что пробел в числах недопустим).

### 4.12. Ревью и дом. задание (12 мин)
Сверить ответы. Вопросы ревью:
- PK нужен, даже если строки «похожи», — чтобы точно указать одну строку и связать таблицы.
- M:N без третьей таблицы невозможна, потому что таблица не умеет «список в ячейке».
- Связь 1:N «хранит» заказ (на стороне многих), потому что один пользователь может иметь много заказов — FK в `orders`.
- Аналитик называет уникальные идентификаторы в требованиях, потому что по ним системы ссылаются на объекты.

Разобрать ДЗ и дать подсказку к вопросу №4: «пустит ли БД заказ с несуществующим user_id?» — нет, внешний ключ запретит нарушение целостности.

## 6. Типичные ошибки и как реагировать

| Ошибка | Реакция учителя |
|---|---|
| «Строка = колонка» перепутаны | Вернуть к аналогии «анкета»: строка — одна анкета, колонка — поле |
| Путает PK и FK | Таблица-шпаргалка: PK — «в этой таблице мой номер», FK — «номер из другой таблицы» |
| «В ячейке можно хранить список» (M:N) | Показать, почему нельзя; ввести `order_items` через пример чека |
| Кладёт FK на сторону «один» | Вопрос: «сколько заказов у пользователя? Много. Значит ключ — у заказа» |
| Забывает кавычки или LIMIT | Напомнить: строки — в кавычках, числа — без; LIMIT — всегда число |
| Пишет `price < 50 000` с пробелом | Объяснить: пробел ломает запрос, формат данных строго задан |
| Не отличает WHERE и показать все строки | Проговорить: WHERE — «фильтр», без него вернутся все строки |
| AS «мне показалось, переименовало таблицу» | Показать: колонка в БД прежняя, меняется только подпись в результате |
| «Зачем PK, они и так различаются» | Придумать двух людей с одинаковыми именем и датой рождения — без id их спутаешь |

## 8. Домашнее задание — разбор и ответы

1. **Библиотека.** Таблицы: `readers` (id PK, name, phone), `books` (id PK, title, author), `issues` (id PK, reader_id FK, book_id FK, date, return_date). Связи: readers 1:N issues, books 1:N issues; читатель—книга M:N через issues. Аналог `order_items` — `issues`.
2. **5 запросов с WHERE** (примеры):
   - `SELECT name FROM products WHERE price >= 10000;`
   - `SELECT name, price FROM products WHERE stock = 0;`
   - `SELECT * FROM orders WHERE total > 5000;`
   - `SELECT email FROM users WHERE name LIKE 'И%';`
   - `SELECT name FROM products WHERE id IN (1, 3, 5);`
   **2 запроса с ORDER BY + LIMIT**:
   - `SELECT name, price FROM products ORDER BY price DESC LIMIT 3;`
   - `SELECT id, date, total FROM orders ORDER BY date ASC LIMIT 5;`
3. **Требование «заказы за последний месяц»**:
   `SELECT * FROM orders WHERE user_id = 1 AND date >= '2026-08-14' ORDER BY date DESC;`
   Объяснение человеческими словами: «показать все заказы пользователя 1 с 14 августа текущего года, новые сверху». Обратить внимание, что точный синтаксис зависит от типа колонки `date` (в предметной области часто `date`/`datetime`).
4. **Вопрос про `user_id` без пользователя**: БД с внешним ключом **не пустит** такую строку — сработает ограничение целостности FOREIGN KEY. Если FK не объявлен, БД пропустит «сироту» — и это тот случай, где в требованиях надо явно описать поведение.

## 10. Заметки по проведению

- Главный риск — слишком долгая теория: на SELECT должно остаться не меньше 25 минут практики.
- Для «слабого» ученика практика 2 — только задания 1–3; усилия направлять на чтение запросов, а не на скорость написания.
- Хорошо работает правило: каждый запрос ученик «проговаривает русскими словами» вслух — это развивает перевод «бизнес → SQL», ключевой для аналитика навык.
- Mermaid-схемы лучше рисовать вместе с учеником от руки/в тексте: сначала связи «пользователь-заказ», потом добавлять товары. Так «рождается» order_items на глазах.
- Держите наготове скриншоты результатов запросов, если практическая среда вдруг недоступна.
