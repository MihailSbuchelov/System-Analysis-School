# Урок 8. Текст для учителя

**Слои и базовые паттерны, управление зависимостями**
Модуль 1, урок 8 · 90 минут · уровень: джун-мидл → аналитик

---

## 1. Цели урока

После урока ученик умеет:

- объяснить, зачем ПО делят на слои и какие это слои;
- описывать правило зависимостей («логика зависит от абстракций»);
- называть и объяснять простыми словами паттерны: Repository, Service, Factory, Observer, DI;
- рисовать слои своего учебного сервиса с указанием места каждого шага;
- связывать «слои» с будущей работой аналитика: use-case → Service, данные → Repository.

**Не цель урока:** детально программировать паттерны, выбирать DI-контейнеры, сравнивать реализации. Фокус — понимание «скелета» системы.

## 4. Сценарий по шагам

### 4.1. Вступление (3 мин)
Объявить тему. Связать: «Мы уже знаем щиты системы снаружи (HTTP, БД). Сегодня — как система устроена изнутри».

### 4.2. Зачем слои (5 мин)
Задать вопрос: «Что будет, если весь код свалить в один файл/модуль?» Выслушать ответы, подвести к причинам: порядок, тестируемость, замена деталей, понятность.

**Акцент для аналитика:** аналитик описывает «чем занимается система» (бизнес-логика) и «как хранит данные» — это два разных слоя, и в ТЗ эти части разделяют.

### 4.3. Три классических слоя (8 мин)
Разобрать таблицу слайда «Три классических слоя». Показать на примере «магазина»:
- Представление: страницы, JSON-эндпоинты.
- Приложение: правила («нельзя заказать без товара на складе»).
- Данные: таблицы из уроков 3–5.

Метафора: «ресторан» — зал (представление) / кухня (логика) / склад (данные). Официант не лезет на склад напрямую.

### 4.4. Правило зависимостей (7 мин)
Объяснить главную идею: верхние слои не знают о деталях нижних. Показать слайд-цитаты. Обсудить: «что случится, если логика жёстко привязана к конкретной БД?» (замена БД = переписывание логики). Упомянуть DI как механизм соблюдения правила.

### 4.5. Паттерны (10 мин)
- **Repository:** логика просит «сохранить заказ», не пишет SQL. Аналог: менеджер в ресторане не идёт на склад — он отдаёт наряд кладовщику.
- **Service:** оркестрация шагов. Показать шаги «Оформить заказ» и заметить: те же шаги аналитик пишет в use-case (модуль 3).
- **Factory:** фабрика создания объектов. Привести пример «оплата по типу».
- **Observer:** издатель/подписчики. «Заказ создан» → склад, бухгалтерия, уведомления. Отметить, что это основа событийного подхода (урок 9).

### 4.6. DI (7 мин)
Показать «плохо» (внутри создаётся БД) vs «хорошо» (передаётся снаружи). Проговорить выгоду для тестов: легко подставить заглушку. Отметить разницу понятий: DI — приём передачи зависимостей; контейнер — инструмент, в уроке не обязателен.

### 4.7. Полная картина (5 мин)
Слайд «Слои учебного магазина целиком». Пройти весь путь: браузер → контроллер → Service → Repository → БД, плюс событие → уведомления. Связать с уроками 1–7: HTTP, БД, ООП, SOLID. Задать вопрос: «где здесь “точки расширения”?» — например, добавить новый способ оплаты = новый Service/Factory, не трогая остальное (перекличка с О — открытость/закрытость из урока 7).

### 4.8. Практика 1 (10 мин)
Ученик раскрашивает шаги кейса. Ожидаемый ответ:
1. Браузер показывает форму → **представление**.
2. Проверка заполнения → **приложение**.
3. Сохранение в таблицу → **данные**.
4. Возврат «сохранено» → **представление**.
Разобрать спорные случаи: «проверка формата e-mail» — обычно представление; «проверка бизнес-правила» — приложение.

### 4.9. Практика 2 (15 мин)
Ученик предлагает хранилища/сценарии/события для своего сервиса. Эталон для «магазина»:
- Repository: `ТоварыRepository`, `ЗаказыRepository`, `ПользователиRepository`.
- Service: `ОформитьЗаказ`, `ОплатитьЗаказ`, `ВернутьТовар`.
- События: «заказ создан», «оплата проведена».
Разобрать ответы, следить, чтобы названия были «из предметной области», а не «из кода» (контроллер — не сценарий).

### 4.10. Ревью (6 мин)
Обсудить вопросы слайда. Ключевая мысль для закрепления: «слои — это язык, которым аналитик и разработчик описывают систему согласованно».

### 4.11. Домашнее задание (4 мин)
Разобрать формулировки, дать подсказки к №3 (DI для тестов: подменить репозиторий фальшивкой) и №4 (Repository прячет SQL и связи БД; «класс с SQL» — это уже жёсткая привязка к БД).

## 5. Чек-лист оценивания

| Критерий | Признак усвоения |
|---|---|
| Слои | Называет 3 слоя и их ответственность |
| Правило зависимостей | Объясняет, почему логика не должна знать детали БД |
| Repository | Описывает как «посредник», не пишет SQL внутри логики |
| Service | Сопоставляет шаги сценария с бизнес-логикой |
| Observer | Объясняет «издатель–подписчик» на своём примере |
| DI | Объясняет «передать снаружи», приводит пример для теста |
| Применение | Рисует слои своего сервиса с ролями шагов |

**Порог:** уверенно объясняет 5 из 7 критериев.

## 6. Типичные ошибки и как реагировать

| Ошибка | Реакция учителя |
|---|---|
| «Слой = папка в коде» | Уточнить: слой — логическая ответственность, папка лишь следствие |
| «Репозиторий — это просто класс с SQL» | Напомнить задачу: изоляция хранения от логики, замена без переписывания |
| «DI — это только для тестов» | Показать ещё выгоду: меньше жёстких связей, легче расширять |
| Путает Service и Factory | Зафиксировать: Service — про «шаги сценария», Factory — про «создание объектов» |
| «Микросервисы избавляют от слоёв» | Подчеркнуть: слои есть внутри каждого сервиса |
| Называет контроллер «сервисом» | Ввести разграничение: контроллер — вход из внешнего мира, Service — бизнес-логика |

## 7. Вопросы для сильного ученика

- «Как слои связаны с SOLID из прошлого урока?» (S — единственная ответственность слоя; D — инверсия зависимостей).
- «Где живёт проверка прав пользователя?» (обычно на границе слоёв: аутентификация при входе, авторизация логики).
- «Что произойдёт с Observer, если подписчиков станет тысячи?» (очереди, гарантии доставки — мост в модуль 3, интеграции).

## 8. Домашнее задание — разбор и ответы

1. **Слои сервиса:** рисунок с тремя слоями; на схеме контроллер (представление), Service (приложение), Repository (данные).
2. **Use-case «Оформить заказ»:** шаги (проверка корзины → остатки → создание заказа → событие) с пометками слоёв (приложение, данные, представление на выдаче ответа).
3. **Пример DI:** «Тест: сервис получает фальшивый репозиторий и проверяет логику без БД».
4. **Repository vs «класс с SQL»:** первый изолирует хранение за интерфейсом, позволяет заменить БД и тестировать логику; второй жёстко связывает.
