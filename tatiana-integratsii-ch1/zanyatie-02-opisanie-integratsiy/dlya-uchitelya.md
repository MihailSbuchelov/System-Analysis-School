## 4. Сценарий по шагам

### 4.1. Вступление (5 мин)
Спросить про формат ч.1: «диалог помог или мешал темпу?» — зафиксировать. Объявить план.

### 4.2. Контракт (10 мин)
Не давать определение сразу. Спросить: «что такое контракт между двумя системами?» Ожидаю: «договор, что кто что отдаёт». Довести: это **требование**, не псевдокод. 7 составляющих — перечислить, она дополняет. Ключевая фраза: **«пока контракт не сломан, вторая сторона не заметит твоих внутренних изменений»**.

### 4.3. Структура эндпоинта (15 мин)
Таблица из презентаци.md §2. Пройти построчно с примером `POST /orders`.
Нейминг: `/payment-methods` (дефисы, множественное число). Ловушка: «почему не `POST /createOrder`?» — REST-философия: ресурс + метод. **Исключение:** действия без собственного ресурса — `POST /orders/123/cancel` допустимо (sub-action). Спросить её: «а `POST /orders/123/pay` — это ок?» (ок, если «оплата» — под-действие заказа).

### 4.4. Схемы данных (15 мин)
Таблица полей. Грабли — по одному, с вопросом:
- **Деньги:** «double?» → нет, float: `0.1+0.2 ≠ 0.3`. Integer в копейках.
- **Даты:** «строка "01.02.2026"?» → нет, ISO 8601. `date` vs `datetime` — разные типы.
- **«Может быть пусто»:** `null` / `""` / отсутствует — выбрать и зафиксировать.
- **Enum:** не перечислены значения → потребитель не знает, что придёт.
- **Массив:** minItems/maxItems — есть ли ограничение (1..100 позиций в заказе).

### 4.5. Ошибки (13 мин)
Ключевое: ошибка = ответ, не «исключение». Единая структура:
```json
{ "errorCode": "ITEM_NOT_FOUND", "message": "Товар 42 не найден", "details": {...} }
```
- `errorCode` — машинный (ветвление логики), `message` — человекочитаемое.
- Словарь кодов на эндпоинт.
Статусы: повторить 401/403 (нет токена / нет прав), добавить:
- `409` — состояние не позволяет (заказ уже оплачен, товар закончился) — **частый вопрос собеса**.
- `422` — синтаксис ок, семантика нет (дата в будущем).
Вопрос: «409 vs 400 — чем?» (400 — битый запрос/валидация полей; 409 — запрос валидный, но состояние не даёт).

### 4.6. Версионирование (12 мин)
3 стратегии: URL (`/api/v1/`), заголовок (`Accept`), query. URL — практично, заголовок — чище.
**Breaking vs non-breaking** — ядро:
- non-breaking: добавить необязательное поле, новый эндпоинт, новый enum-значения (с предупреждением).
- breaking: удалить/переименовать поле, изменить тип, убрать enum-значение, изменить семантику.
Вопросы:
- «Добавили `priceVat` — breaking?» (нет).
- «Переименовали `price` → `amount`?» (breaking, новая версия).
- «Убрали значение из enum `status`?» (breaking).
Правило: v1 и v2 параллельно N месяцев → деградация v1.

### 4.7. OpenAPI (10 мин)
Показать Swagger Editor или готовый YAML (petstore). Разобрать: `openapi`, `info`, `paths`, `components/schemas`, `$ref`.
Что генерируется: документация (Swagger UI), mock-сервер, клиентский код, контракт-тесты, импорт в Postman.
Фраза для собеса: «описываю в OpenAPI 3.x, генерирую доки и моки, валидация через schema».
Не требуется писать руками — знать структуру, читать.

### 4.8. Безопасность (встроено в OpenAPI-блок, 2 мин)
`securitySchemes`: bearer, apiKey, oauth2. Секреты — никогда в ТЗ. API key vs Bearer: один ключ на всё, нет срока жизни, сложно отозвать.

### 4.9. Практика (15 мин)
**Кейс А:** `POST /api/v1/rentals` (аренда оборудования). Она описывает: путь, body (3–5 полей: `equipmentId`, `startDate`, `endDate`, `customerRef`), ответы: `201` → Rental, `400` (валидация), `409` (объект занят на дату), `401`. Проверить: деньги? (нет), даты ISO? (да), enum статуса? (да).
**Кейс Б:** `GET /api/v1/products` + фильтр по категории + пагинация.
- Query: `category`, `page`, `size`.
- Ответ: envelope `{ items: [...], page, size, total }`.
- Breaking? (нет, добавили query params — backward compat).
- Нужен v2? (нет).

## 5. Чек-лист оценивания

| Критерий | Признак усвоения |
|---|---|
| 7 составляющих контракта | Перечисляет без подсказки |
| Эндпоинт | Описывает метод/путь/body/ответы полностью |
| Нейминг | `/payment-methods`, не `/PaymentMethods`; знает исключение sub-action |
| Схемы | Деньги integer, даты ISO 8601, enum перечислен, null-политика |
| Ошибки | Единая структура, errorCode+message, словарь; 401/403/409/422 |
| Версионирование | 3 стратегии, breaking/non-breaking на примерах |
| OpenAPI | Читает paths/schemas/$ref, знает что генерируется |
| Чек-лист | Заполняет 11 пунктов для своего кейса |

**Порог:** 5 из 8 уверенно. Красный флаг: путает 409/400 или не знает про breaking — зафиксировать в ДЗ.

## 6. Типичные ошибки и как реагировать

| Ошибка | Реакция |
|---|---|
| «Контракт = спецификация» | Развести: спецификация шире (бизнес-правила), контракт — только граница |
| `POST /createOrder` | Вернуть к REST: ресурс + метод; sub-action допустим (`/orders/123/cancel`) |
| Деньги `double` | Float-арифметика: `0.1+0.2=0.30000000000000004`; integer в копейках |
| Дата «01.02.2026» | ISO 8601: `2026-02-01` (date) или `2026-02-01T10:00:00Z` (datetime) |
| «Ошибки — это исключения, не описываем» | Ошибка = ответ с телом; единая структура обязательна |
| 409 = 400 | 400 — битый запрос; 409 — запрос ок, состояние не позволяет |
| «Версия = просто число в URL» | Развести 3 стратегии; URL — самая простая, заголовок — чище |
| «Добавить поле — breaking» | Non-breaking: старый клиент просто не увидит новое необязательное поле |
| OpenAPI «это Swagger UI, красивая страница» | OpenAPI — формат (YAML/JSON), UI — один из потребителей |

## 10. Заметки по проведению

- Если формат ч.1 «диалог» сработал — продолжать. Если нет — «рассказываю → резюмируй 3 фразами в конце блока».
- **Якорь «money is integer, date is ISO 8601»** — если не помнит через занятие, повторить на старте каждого следующего.
- **Якорь breaking vs non-breaking** — 3 примера (добавить поле / переименовать / убрать enum) — если называет все 3 правильно, занятие прошло.
- Практика: не давать «идеальный» контракт. Дать её проект, найти 2–3 дыры, она сама их находит (по чек-листу).
- Не углубляться в OAuth-флоу — это модуль безопасности. Здесь только «тип auth в securitySchemes».
