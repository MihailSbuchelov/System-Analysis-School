## 1. Контракт — «закон» между системами

**Контракт интеграции** — это точное описание: **что** одна система посылает другой, **в каком виде**, **что** получит в ответ и **что будет**, если что-то пошло не так.

Почему он «закон»:
- по нему работают **две стороны независимо**: ты меняешь свою реализацию — пока контракт не сломан, вторую сторону это не трогает
- на собесе спрашивают: «как вы описываете API?» — ответ «табличка в Confluence с названиями полей» = красный флаг
- контракт = **требование**, а не «псевдокод». В нём нет «как сделать», только «что отдаёте/принимаете»

**Что входит в контракт:**
1. Эндпоинты (метод + путь)
2. Формат запроса: query params, body, заголовки
3. Формат ответа: тело, статусы
4. Структура данных (схемы)
5. Ошибки: какие, какого вида
6. Версия
7. Аутентификация (тип, не сами ключи)

**Вопрос:** чем контракт отличается от «спецификации»? (подсказка: спецификация — шире, в неё могут входить и бизнес-правила; контракт — только «граница обмена»)

## 2. Структура REST-контракта

На каждый эндпоинт описываем:

| Поле | Пример |
|---|---|
| Метод | `POST` |
| Путь | `/api/v1/orders` |
| Заголовки | `Authorization: Bearer {token}`, `Content-Type: application/json` |
| Query params | `page`, `size`, `status` |
| Body (схема) | `CreateOrderRequest` |
| Ответы | `201` → `Order`, `400` → `Error`, `401` → `Error`, `409` → `Error` |

Пример (псевдо-JSON для ТЗ):

```
POST /api/v1/orders
Headers:
  Authorization: Bearer {token}
  Content-Type: application/json
Body: CreateOrderRequest
Responses:
  201 -> Order (Location: /api/v1/orders/{orderId})
  400 -> Error (валидация полей)
  401 -> Error (нет токена / истёк)
  409 -> Error (товара нет в наличии)
  500 -> Error (ошибка сервера)
```

**Правила, которые проверяют на собесе:**
- ресурс — множественное число, строчные, дефисы: `/payment-methods`, не `/PaymentMethods`
- действия не в имени ресурса, если есть REST-метод: `POST /orders`, не `POST /createOrder`
- вложенные ресурсы: `GET /orders/123/payments`

**Вопрос:** почему `POST /createOrder` — плохой стиль? А когда допустимые исключения (нестандартные «действия» типа `POST /orders/123/cancel`)?

## 3. JSON-схема данных

Для каждого объекта — таблица полей:

| Поле | Тип | Обязательное | Ограничения | Описание |
|---|---|---|---|---|
| id | integer | да | > 0, генерируется сервером | ID заказа |
| userId | integer | да | > 0 | Кто разместил |
| items | array[OrderItem] | да | 1..100 элементов | Позиции |
| total | integer | да | > 0, в копейках | Сумма |
| status | string | да | enum: `NEW`, `PAID`, `CANCELLED` | Статус |
| createdAt | string (ISO 8601) | да | формат `YYYY-MM-DDTHH:mm:ssZ` | Время создания |

**Типичные ошибки аналитика в схемах:**
- деньги — `double` (НЕТ: округления, `float` — только целые в минимальной единице: копейки/центы)
- дата — `string "01.02.2026"` (НЕТ: ISO 8601, лучше `date` vs `datetime` разделять)
- «может быть пусто» — не описано: `null` допустимо? или `""`? или поле отсутствует?
- enum — не перечислены значения
- массив — нет границ (min/max элементов)

**Вопрос:** почему деньги не `double`? Что будет с `0.1 + 0.2` в float?

## 4. Ошибки как часть контракта

Ошибка — это **ответ**, а не «исключение». В контракте описываем:

1. **Статус-код** (4xx/5xx) — уже обсудили в ч.1, но теперь строго по эндпоинту
2. **Структура тела ошибки** — единая для всех эндпоинтов:

```json
{
  "errorCode": "ITEM_NOT_FOUND",
  "message": "Товар 42 не найден",
  "details": {
    "field": "items[0].sku",
    "value": "SKU-42"
  }
}
```

3. **Словарь error-кодов** для эндпоинта: `ITEM_NOT_FOUND`, `DUPLICATE_ORDER`, `INSUFFICIENT_STOCK`…

**Правила:**
- `message` — человекочитаемое, `errorCode` — машинный (по нему другая система ветвит логику)
- 4xx — вина клиента, 5xx — сервера (мнемоника ч.1)
- `401` vs `403` — нет токена vs нет прав (частый вопрос собеса, повторить)
- `409 Conflict` — когда состояние не позволяет (заказ уже оплачен, товар закончился)
- `422 Unprocessable` — синтаксис ок, но семантика нет (например, дата рождения в будущем)

**Вопрос:** чем `409` отличается от `400`? Приведи по 2 примера.

## 5. Версионирование

**Почему нужно:** контракт меняется. Клиенты (другие системы) не могут одновременно «переезжать» — нужна совместимость.

**Стратегии:**
1. **URL-версия:** `/api/v1/orders`, `/api/v2/orders` — просто, понятно, дорого (двойная поддержка)
2. **Заголовок:** `Accept: application/vnd.mycompany.v2+json` — чище, но сложнее для клиентов
3. **Query param:** `?version=2` — не очень, но встречается

**Совместимость — главное:**
- **Назад-совместимо (breaking не):** добавить необязательное поле, новый эндпоинт, новый статус 2xx — старые клиенты работают
- **Breaking:** удалить/переименовать поле, изменить тип, изменить enum (убрать значение), изменить семантику статуса

**Правила (запомни для собеса):**
- добавлять — можно, удалять — только в новой версии
- enum: добавлять значения можно (предупредить), убирать — только breaking
- «мягкий» переход: v1 и v2 живут параллельно N месяцев, затем v1 деградируется

**Вопрос:** клиент ждёт поле `price` (integer). Мы решили добавить `priceVat` (integer). Это breaking? А если переименовать `price` → `amount`?

## 6. OpenAPI: зачем аналитику

**OpenAPI** (бывш. Swagger) — машиночитаемый формат описания REST API (YAML/JSON).

Зачем аналитику:
- **единый источник правды**: из него генерируется документация, mock-сервер, клиентский код, тесты
- **валидация**: можно автоматически проверить, что запрос/ответ соответствует схеме
- **собес**: «описываю контракты в OpenAPI, генерирую документацию, передаю в Postman для проверки»

Минимальный фрагмент (знать, что такое, не писать руками):

```yaml
openapi: 3.0.0
info:
  title: Orders API
  version: 1.0.0
paths:
  /orders:
    post:
      summary: Создать заказ
      requestBody:
        content:
          application/json:
            schema:
              $ref: '#/components/schemas/CreateOrderRequest'
      responses:
        '201':
          description: Создан
          content:
            application/json:
              schema:
                $ref: '#/components/schemas/Order'
        '400':
          description: Ошибка валидации
components:
  schemas:
    CreateOrderRequest:
      type: object
      required: [userId, items]
      properties:
        userId:
          type: integer
        items:
          type: array
          minItems: 1
          items:
            $ref: '#/components/schemas/OrderItem'
```

Инструменты: Swagger Editor (онлайн), Swagger UI (просмотр), Postman (импорт/экспорт).

**Вопрос:** что из этого можно сгенерировать автоматически? (документация, mock, клиент, контракт-тесты)

## 7. Безопасность контракта (объёмно для ТЗ)

В контракте описываем **тип** аутентификации, не сами секреты:
- `Bearer token` (JWT) — `Authorization: Bearer <token>`
- API key — `X-Api-Key: <key>`
- mTLS — для B2B с банками
- OAuth 2.0 client credentials — сервис-к--сервису

**Правила:**
- секреты (ключи, токены) — **никогда** в ТЗ и в коде, только способ их получения (vault, env)
- TLS — обязательный заголовок в требованиях, не «опционально»
- что с rate limit: `429 Too Many Requests` + заголовок `Retry-After`

**Вопрос:** чем API key хуже Bearer token? (подсказка: один ключ на всё, сложно отозвать/передавать, нет срока жизни по умолчанию)

## Резюме занятия (проговори в конце)

- Контракт = закон между системами: что, в каком виде, что в ответ, что при ошибке.
- Структура эндпоинта: метод, путь, заголовки, body, ответы — всё описано.
- Схемы данных: типы, обязательность, ограничения; деньги — integer, даты — ISO 8601.
- Ошибки — часть контракта: единая структура, `errorCode` + `message`, словарь.
- Версионирование: URL-версия, backward/forward compat, breaking vs non-breaking.
- OpenAPI: машиночитаемый контракт, генерация доков/моков/клиентов.
- Безопасность: тип auth в ТЗ, секреты — никогда.
