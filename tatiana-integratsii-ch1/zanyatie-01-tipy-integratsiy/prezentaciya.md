## 1. Что такое интеграция

**Интеграция** — это способ, которым **две (или больше) системы обмениваются данными или действиями**.

Примеры:
- сайт Авито спрашивает у платёжного сервиса «можно ли снять 5000 с карты»
- CRM передаёт в 1С «сделка закрыта»
- сервис аналитики раз в день выгружает отчёт из БД в витрину данных

**Почему это важно для аналитика:**
- интеграция — это **граница систем**. На границе живёт большинство проблем: таймауты, повторные запросы, несовпадение данных, кто отвечает за ошибку
- на собесе любят спрашивать: «какую интеграцию вы бы выбрали и почему?» — ответ без альтернативы и минусов = минус балл

> **Ключевая мысль занятия:** не бывает «лучшей» интеграции. Есть **контекст**: сколько данных, насколько важна скорость, что делать при ошибке, кто участвует. Задача аналитика — выбрать и **обосновать**.

**Вопросы (скажи своими словами):**
- Чем интеграция отличается от «просто базы данных, которую читают два приложения»?
- Что на границе между системами может пойти не так? Назови хотя бы 3.

## 2. Большое разделение: синхронное vs асинхронное

Это **первое и главное** разделение. Сначала его, потом детали.

**Синхронная интеграция** — я спросил и **жду ответ сейчас**.
- «Взять кредит на 100 000» → банк должен сказать «да/нет» прямо сейчас, клиент ждёт на странице
- Примеры: REST API, SOAP, gRPC

**Асинхронная интеграция** — я **положил сообщение/событие и пошёл дальше**. Кто-то другой, в другое время, его обработает.
- «Заказ оплачен» → система лояльности узнает об этом через 1–5 секунд, пользователю это неважно
- Примеры: очереди сообщений, событийные шины (Kafka, RabbitMQ)

| Критерий | Синхронная | Асинхронная |
|---|---|---|
| Ждём ответ? | Да, сразу | Нет |
| Пользователь ждёт? | Обычно да | Нет |
| Связанность систем | Высокая: упал один — второй ждёт/падает | Низкая: системы не знают о существовании друг друга |
| Когда ответ «сейчас» критичен? | Да | Нет |
| Сложность отладки | Проще (запрос–ответ) | Сложнее (нужны трейсинг, логи) |
| Пример | «Проверить баланс карты» | «Начислить баллы после покупки» |

**Вопросы:**
- Почему нельзя асинхронно проверить, хватит ли денег на карте?
- Почему лояльность (баллы) нормально асинхронная, а списание денег — нет?

## 3. Синхронные интеграции

### 3.1. REST (основной)

- HTTP + JSON (иногда XML)
- Методы GET/POST/PUT/PATCH/DELETE, статус-коды 2xx/4xx/5xx
- **Плюсы:** простой, понятный, везде поддерживается, легко отлаживать (Postman, curl), огромный инструментарий (OpenAPI)
- **Минусы:** «тяжеловесные» текстовые данные, слабая типизация контракта (JSON — просто формат), при высокой нагрузке хуже бинарных протоколов
- **Когда:** 90% интеграций внутри компании и B2B, веб/API для клиентов

### 3.2. SOAP — «читать и понимать»

- Строгий протокол: всё в XML, есть **конверт (Envelope/Header/Body)**, контракт описывается в **WSDL**
- Встроены надёжность: WS-Security (авторизация на уровне протокола), WS-ReliableMessaging (гарантированная доставка)
- **Почему жив:** банки, АБС, государственные системы, B2B с регуляторными требованиями
- **Плюсы:** формальный контракт (WSDL), встроенные механизмы безопасности/надёжности
- **Минусы:** громоздкие сообщения, медленнее, мало новых проектов
- **Задача аналитика:** уметь **читать** WSDL, понимать структуру конверта, не путать с REST. Проектировать с нуля SOAP почти никто не просит.

**SOAP vs REST — таблица для запоминания:**

| | SOAP | REST |
|---|---|---|
| Формат | только XML | JSON (чаще), XML |
| Контракт | WSDL (формальный) | OpenAPI (формальный, но проще) |
| Протокол | может идти по HTTP и не только | HTTP |
| Безопасность | встроена в протокол (WS-Security) | обычно TLS + токены/ключи |
| Где встречается | банки, АБС, госсектор, legacy | почти все новые проекты |

### 3.3. gRPC (быстро, для насмотренности)

- Бинарный протокол поверх HTTP/2, контракт в protobuf (`.proto` файлы)
- **Плюсы:** быстрый, строгая типизация, стриминг
- **Минусы:** нечитаемый «для человека» трафик, меньше инструментов отладки, не проходит через некоторые прокси/ограничители
- **Когда:** высоконагруженные внутренние сервисы. На собесе достаточно: «знаю, что такое, когда применяется, чем отличается от REST».

## 4. Асинхронные интеграции

### 4.1. Две модели обмена

**Point-to-point (очередь):** одно сообщение — одному получателю.
- «задача: отправить письмо» → воркер её забирает
- Пример: RabbitMQ

**Pub/Sub (события):** одно событие — множеству подписчиков.
- «заказ создан» → подписаны: лояльность, логистика, аналитика, уведомления
- Пример: Kafka (а точнее Kafka Topics с подписками)

### 4.2. Что аналитик обязан держать в голове

1. **Гарантии доставки:** сообщение может потеряться, доставлено два раза, доставлено в другом порядке. В требованиях прописываем, что допустимо.
2. **Идемпотентность потребителя:** если событие «оплата прошла» пришло дважды — начислить баллы один раз. Это **обязательное** требование к потребителю событий.
3. **Что делать, если обработчик упал:** повтор (retry), мёртвое письмо (dead letter), ручной пересчёт.
4. **Порядок:** нужен ли порядок событий по сущности (заказу)? В Kafka — внутри партиции порядок есть.

### 4.3. Kafka — «что это и когда брать»

- Это **журнал событий** (лог): события не «съедаются», а сохраняются; потребитель читает со своего смещения
- **Топик** → **партиции** (распараллеливание записи/чтения) → **consumer group** (группа потребителей, каждая партиция одной)
- **Когда брать:** большие объёмы событий, события нужно «пережевывать» повторно (аналитика), много подписчиков, требуется история
- **Когда НЕ брать:** простые очереди задач (там хватит RabbitMQ или даже очереди БД), «мне нужно, чтобы один запрос получил ответ» (это синхронная история)

**Kafka vs RabbitMQ (для собеса):**
- RabbitMQ — классическая очередь сообщений, гибкие маршрутизации, «достал и забыл»
- Kafka — журнал, хранение, повторное чтение, параллелизм; «мне нужна лента событий»
- Грубое правило: очередь задач — RabbitMQ; поток событий + аналитика + много подписчиков — Kafka

**Вопросы:**
- Система начисления баллов получает событие «оплата прошла» дважды. Что должно быть в требованиях, чтобы баллов не стало вдвое?

## 5. Файловые интеграции и ETL

### 5.1. Файл по расписанию (SFTP)

- Система А выгружает CSV/Excel/XML → кладёт на SFTP → система Б по расписанию забирает и импортирует
- **Плюсы:** очень просто, нет «живой» зависимости, хорошо для больших объёмов, «история» файла
- **Минусы:** задержка (минуты/часы/дни), проблемы с контролем ошибок (частично импортирован файл?), версиями, дублями
- **Когда:** отчёты, выгрузки для 1С, миграции данных, B2B с партнёрами без API

**Типичные грабли (обязательно знать):**
- файл записывается не целиком → импорт «половинки» (решение: выкладывать как `file.tmp` → переименовать в `file.csv`)
- повторный импорт дублирует строки (решение: идемпотентный импорт по ключу, маркер «файл обработан»)
- изменилась структура файла → молча ломаются данные (решение: проверка шапки/схемы)

### 5.2. ETL

**ETL = Extract → Transform → Load**: выгрузить из источника, преобразовать, загрузить в витрину (обычно ДМ/отчётную БД).
- Редкие «ручные» интеграции (раз в месяц), большие объёмы, данные из многих источников в один отчёт
- Аналитик описывает: источники, периодичность, правила трансформации (маппинг полей), что делать при ошибке, как проверить результат

## 6. Сравнительная таблица и чек-лист выбора

| Тип | Ответ сейчас? | Объём данных | Надёжность | Сложность | Где встречается |
|---|---|---|---|---|---|
| REST | Да | малый/средний | средняя (retry, идемпотентность) | низкая | большинство API |
| SOAP | Да | средний | высокая (WSDL, WS-*) | средняя | банки, АБС, госсектор |
| gRPC | Да | малый, высокая частота | средняя | средняя | высоконагруженные внутренние |
| Очередь (RabbitMQ) | Нет | средний | высокая | средняя | задачи, письма, биллинг |
| Kafka | Нет | большой, поток | высокая | высокая | события, аналитика, many subscribers |
| Файл/SFTP | Нет | большой | средняя (ручной контроль) | низкая | отчёты, 1С, B2B-legacy |
| ETL | Нет (пакет) | очень большой | средняя | средняя | ДМ, отчётность |

### Чек-лист выбора (запомни, на собесе отвечай по нему)

1. **Нужен ответ «прямо сейчас»?** Да → синхронная (REST/SOAP/gRPC). Нет → можно асинхронная.
2. **Что будет, если вторая система упала?**
   - нельзя потерять операцию → синхронная с retry или асинхронная с гарантированной доставкой (очередь/Kafka)
   - можно потерять/повторить позже → файл по расписанию, событие без SLA
3. **Сколько данных и с какой частотой?**
   - много + поток событий → Kafka
   - много + раз в день → файл/ETL
   - по чуть-чуть часто → REST
4. **Кто вторая система?**
   - банк/АБС/gov, «у них SOAP» → SOAP (читать)
   - наш сервис → REST (или gRPC, если внутри и нагрузка)
   - партнёр без API → файл
5. **Кто ещё потребляет эти данные?**
   - один → очередь p2p или REST
   - много подписчиков, история нужна → Kafka
6. **Есть ли у второй стороны требование к формату?** (банк — XML/SOAP, партнёр — CSV)

**Формула ответа на собесе:** «Я бы выбрал(а) X, потому что [контекст: скорость/надёжность/объём/кто вторая сторона]. Альтернатива — Y, она была бы лучше, если [условие]. Минусы X — [назвать честно].»

## 7. Практика: выбери тип и обоснуй

Для каждого кейса: (1) тип, (2) почему, (3) альтернатива и когда она была бы лучше.

**Кейс 1.** Пользователь платит картой. Приложение должно показать «оплата прошла» до того, как человек закроет вкладку.
**Кейс 2.** После оплаты сервис лояльности начисляет баллы, сервис статистики пишет в отчёт, сервис push-уведомлений шлёт «спасибо за покупку».
**Кейс 3.** Раз в ночь склад выгружает остатки товаров (2 млн строк) в систему мерчанта.
**Кейс 4.** Нужно интегрироваться с АБС банка (1С БУХ / Directum). У них «всё как у всех банков».
**Кейс 5.** Внутренние микросервисы: сервис заказов и сервис инвентаря должны знать о изменении остатка быстро, нагрузка высокая, ответ «сейчас» не нужен.
**Кейс 6.** Раз в месяц бухгалтеру нужен отчёт по 12 источникам в Excel.

(Разбираем устно по одному, 10–12 минут на все.)

## 8. Как аналитик описывает интеграцию в ТЗ (мини-шаблон)

Для каждой интеграции в требованиях:

1. **Участники:** кто отправитель, кто получатель (системы, а не люди)
2. **Тип:** REST / очередь / событие / файл / SOAP…
3. **Направление:** односторонняя / двусторонняя
4. **Триггер:** что запускает обмен (событие, расписание, действие пользователя)
5. **Контракт:** какие данные (ссылка на OpenAPI/схема/шаблон файла)
6. **Частота и объём:** запрос/секунду, строк в выгрузке
7. **Ошибки и повтор:** что при таймауте, при 5xx, при битом файле; retry-политика (сколько раз, с каким интервалом)
8. **Идемпотентность:** что делать при повторной отправке (ключ идемпотентности?)
9. **SLA:** максимальное время доставки/обработки, доступность
10. **Безопасность:** auth (токен/API-key/mTLS), шифрование (TLS), что с секретами

> На собесе, если спросят «как вы описываете интеграцию?», — этот список и есть ответ. Не нужно знать всё про Kafka, нужно показать, что **видишь граничные случаи**.

## Резюме занятия (проговори вслух в конце)

- Интеграция = обмен между системами; на границе живёт 80% проблем.
- Первое разделение: синхронное (ждём ответ) vs асинхронное (положили и поехали).
- Синхронные: REST (основа), SOAP (читать, банки), gRPC (внутри, скорость).
- Асинхронные: очередь p2p (задачи), события/Kafka (многим подписчикам, история).
- Файл/ETL — для больших объёмов и legacy, с граблями: половинки, дубли, смена схемы.
- Выбор = чек-лист (ответ сейчас / упала система / объём / кто вторая сторона / сколько потребителей).
- В ТЗ: 10 пунктов мини-шаблона, из которых джуны чаще всего забывают retry, идемпотентность, SLA.
