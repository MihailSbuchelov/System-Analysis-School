## 1. Что такое интеграция

**Интеграция** — это способ, которым **две системы обмениваются данными или действиями**.

Пример из жизни:
```
[Сайт Авито] ──REST──> [Платёжный сервис] ──SOAP──> [Банк]
   "списать 5000"        "charge(card,5000)"   "дебет счёта"
<── 200 {status:OK} ──<  "ok, tx=99887"       "дебет прошёл"
```

**Почему аналитик описывает интеграцию в требованиях:**
- интеграция = **граница между системами**
- на границе: таймауты, повторные запросы, несовпадение форматов, кто чинит при ошибке
- на собесе: «какую интеграцию выбрал(а) и почему?» — ответ без альтернативы = минус

> **Ключевая мысль:** не бывает лучшей интеграции. Есть контекст: объём, скорость, надёжность, кто вторая сторона.

## 2. Синхронное vs асинхронное

**Синхронная** — спросил, **жду ответ сейчас**.
```
Клиент ──POST /pay {card, 5000}──> Сервер
Клиент <── 200 {status: PAID} ─── Сервер   (прошло 800 мс, клиент ждал)
```

**Асинхронная** — положил сообщение, **пошёл дальше**.
```
Сервер заказов ──publish "order.paid"──> Kafka
(сервер не ждёт, отвечает клиенту 201 сразу)

Kafka ──consume──> Сервис лояльности   (через 2 сек)
Kafka ──consume──> Сервис аналитики    (через 5 сек)
Kafka ──consume──> Сервис push         (через 3 сек)
```

| Критерий | Синхронная | Асинхронная |
|---|---|---|
| Ждём ответ? | Да, сразу | Нет |
| Пользователь ждёт? | Да | Нет |
| Связанность | Высокая (упал один — второй ждёт) | Низкая (системы не знают друг о друге) |
| Отладка | Проще (запрос–ответ) | Сложнее (логи, трейсинг) |
| Пример | «Списать деньги с карты» | «Начислить баллы после покупки» |

**Якорь:** деньги — синхронно (необратимо, клиент ждёт). Баллы — асинхронно (можно пересчитать, задержка некритична).

## 3. Синхронные интеграции

### 3.1 REST

HTTP + JSON (реже XML). Методы GET/POST/PUT/PATCH/DELETE.

Пример запроса/ответа:
```
POST /api/v1/orders HTTP/1.1
Host: api.aviaito.com
Authorization: Bearer eyJhbGciOi...
Content-Type: application/json

{
  "userId": 7,
  "items": [
    {"sku": "SKU-42", "qty": 1}
  ],
  "total": 500000
}

HTTP/1.1 201 Created
Location: /api/v1/orders/123
Content-Type: application/json

{
  "orderId": 123,
  "status": "CREATED",
  "createdAt": "2026-09-20T19:00:00Z"
}
```

#### Типы данных в REST (JSON)

| Тип JSON | Пример | Когда | Грабли |
|---|---|---|---|
| `integer` | `500000` | Счётчики, id, **деньги в копейках** | Не `double` для денег: `0.1+0.2=0.30000000000000004` |
| `number` (float) | `3.14` | Коэффициенты, проценты, geolocation | Не для денег и точных расчётов |
| `string` | `"SKU-42"` | Имена, коды, тексты | Не для дат: `"01.02.2026"` → `"2026-02-01"` (ISO 8601) |
| `string` (date-time) | `"2026-09-20T19:00:00Z"` | Момеent во времени | Всегда с таймзоной (`Z` = UTC) |
| `string` (date) | `"2026-09-20"` | Только дата (без времени) | Не путать с date-time |
| `boolean` | `true` | Флаги: `isAvailable`, `isActive` | Не `0/1`, не `"yes"/"no"` |
| `array` | `[1, 2, 3]` | Списки: items, tags | Указывать minItems/maxItems в схеме |
| `object` | `{"lat": 55.7, "lon": 37.6}` | Вложенные структуры | Не плоские ключи `lat_1`, `lat_2` |
| `null` | `null` | Поле отсутствует (если допустимо) | Лучше: поле **отсутствует** в JSON, а не `null` |

**Правила для аналитика:**
- **Деньги:** `integer` в минимальной единице (копейки/центы). `total: 500000` = 5 000 00 руб.
- **Даты:** ISO 8601. `date` (`2026-09-20`) vs `datetime` (`2026-09-20T19:00:00Z`) — разные типы.
- **Enum:** `string` с перечисленными значениями: `"status": "CREATED"` (не число, не bool).
- **ID:** `integer` или `string` (UUID). Не mix: в одном API все id одного типа.

#### Способы авторизации в REST

| Способ | Как выглядит в запросе | Когда | Плюсы | Минусы |
|---|---|---|---|---|
| **Bearer Token (JWT)** | `Authorization: Bearer eyJhbGciOi...` | Клиенты, внутри, сервис-к-сервису | Срок жизни (1 час), refresh, роли в токене | Нужен сервис выпуска токенов |
| **API Key** | `X-Api-Key: abc123secret` или `?api_key=abc123` | Простые B2B, партнёры | Очень просто, нет срока жизни | Один ключ = все права, сложно отозвать |
| **Basic Auth** | `Authorization: Basic dXNlcjpwdw==` (base64 от login:pass) | Legacy, не без TLS | Простой | Пароль в каждом запросе, нет срока жизни |
| **OAuth 2.0** (client credentials) | `Authorization: Bearer {token из /oauth/token}` | Сервис-к-сервису, B2B | Стандарт, гранулярные права (scopes) | Сложнее: нужен auth-сервер, token exchange |
| **mTLS** | Сертификаты на клиенте и сервере (в TLS handshake) | Банки, высокая безопасность | Двусторонняя аутентификация, нет токенов в заголовках | Сложная инфраструктура (CA, ротация сертификатов) |

**Примеры заголовков:**

```
# Bearer (JWT) — самый частый
Authorization: Bearer eyJhbGciOiJIUzI1NiIsInR5cCI6IkpXVCJ9.eyJzdWIiOiI3Iiwi...

# API Key — простой B2B
X-Api-Key: ak_live_5f8a2c9e1b3d4e6f

# Basic Auth — legacy (только с TLS!)
Authorization: Basic dGVzdF91c2VyOnBhc3N3b3JkMTIz

# OAuth 2.0 — сначала получаем токен:
POST /oauth/token
grant_type=client_credentials
client_id=my_service
client_secret=s3cr3t

→ { "access_token": "eyJ...", "expires_in": 3600, "token_type": "Bearer" }

# Потом используем:
Authorization: Bearer eyJ...
```

**Что писать в ТЗ (а не что хранить):**
- Тип: Bearer / API Key / mTLS
- Срок жизни токена: 1 час, refresh — 30 дней
- Где брать токен: Vault / auth-сервер / env (не в коде!)
- TLS: обязательно, 1.2+

**Секреты (сами ключи, пароли, токены) — никогда в ТЗ и в коде.** Только способ получения.

| Плюс | Минус |
|---|---|
| Простой, везде поддерживается | Текстовый формат (медленнее бинарного) |
| OpenAPI, Postman, curl | Нет встроенной типизации |
| 90% проектов | Нет стриминга |

### 3.2 SOAP

Строгий протокол, только XML. Конверт:

```xml
<soap:Envelope xmlns:soap="http://schemas.xmlsoap.org/soap/envelope/">
  <soap:Header>
    <auth:Token xmlns:auth="http://bank.example.com/auth">
     eyJ0eXAiOiJKV1QiLCJhbGciOiJIUzI1NiJ9...
    </auth:Token>
  </soap:Header>
  <soap:Body>
    <getBalance xmlns="http://bank.example.com/api">
      <accountId>1234567890</accountId>
    </getBalance>
  </soap:Body>
</soap:Envelope>
```

Ответ:
```xml
<soap:Envelope>
  <soap:Body>
    <getBalanceResponse>
      <balance>15000.00</balance>
      <currency>RUB</currency>
      <accountId>1234567890</accountId>
    </getBalanceResponse>
  </soap:Body>
</soap:Envelope>
```

**WSDL** (фрагмент) — контракт SOAP:
```xml
<wsdl:definitions xmlns:wsdl="http://schemas.xmlsoap.org/wsdl/">
  <wsdl:types>
    <xsd:schema>
      <xsd:element name="getBalance">
        <xsd:complexType>
          <xsd:sequence>
            <xsd:element name="accountId" type="xsd:string"/>
          </xsd:sequence>
        </xsd:complexType>
      </xsd:element>
      <xsd:element name="getBalanceResponse">
        <xsd:complexType>
          <xsd:sequence>
            <xsd:element name="balance" type="xsd:decimal"/>
            <xsd:element name="currency" type="xsd:string"/>
          </xsd:sequence>
        </xsd:complexType>
      </xsd:element>
    </xsd:schema>
  </wsdl:types>
  <wsdl:message name="getBalanceRequest">
    <wsdl:part name="parameters" element="tns:getBalance"/>
  </wsdl:message>
  <wsdl:portType name="BankAPI">
    <wsdl:operation name="getBalance">
      <wsdl:input message="tns:getBalanceRequest"/>
    </wsdl:operation>
  </wsdl:portType>
  <wsdl:binding name="BankAPISoap" type="tns:BankAPI">
    <soap:binding transport="http://schemas.xmlsoap.org/soap/http"/>
  </wsdl:binding>
  <wsdl:service name="BankService">
    <wsdl:port name="BankPort" binding="tns:BankAPISoap">
      <soap:address location="https://bank.example.com/api/balance"/>
    </wsdl:port>
  </wsdl:service>
</wsdl:definitions>
```

#### SOAP vs REST — в чём принципиальная разница

Разница **не в формате** (XML vs JSON) и **не в безопасности** (обе могут шифровать). Разница в **уровне, на котором работают правила**:

| | SOAP | REST |
|---|---|---|
| **Где правила** | Внутри сообщения (конверт) | В HTTP-методах и статус-кодах |
| **Структура сообщения** | Обязательный конверт: Envelope → Header + Body. Жёстко задана. | Нет обёртки. JSON/XML в body — что хочешь |
| **Контракт** | WSDL: машиночитаемый, **валидирует** сообщение. Не соответствует WSDL → отклоняется. | OpenAPI: описательный. Можно валидировать, но **не обязателен** на транспорте |
| **Auth** | WS-Security: токен/сертификат **внутри конверта** (в Header). Провайдер может требовать подписанный конверт. | Снаружи: заголовок `Authorization: Bearer ...` или `X-Api-Key`. TLS шифрует канал, не сообщение |
| **Надёжность** | WS-ReliableMessaging: нумерация, ack, retry **на уровне протокола** | Добавляешь сам в приложении (retry, идемпотентность, outbox) |
| **Транзакции** | WS-AtomicTransaction: 2PC на уровне протокола | В приложении (Saga, outbox) |
| **Гибкость** | Низкая: всё в XML, строгая схема | Высокая: JSON, любые форматы, частичные ответы |
| **Отладка** | XML-парсер, громоздко | curl, Postman, JSON — читаемо |

**Почему SOAP жив в банках:** в 2005 году нужен был формальный, машиночитаемый, валидируемый контракт между системами разных вендоров, с гарантированной доставкой и транзакциями **на уровне протокола**, без доверия к приложениям. WS-* давал это "из коробки". REST такого не даёт — всё пишешь сам.

**Почему REST выиграл в остальном:** проще, быстрее отлаживать, JSON легче парсить, OpenAPI достаточен для 90% сценариев, нет XML-парсера.

> **На собесе:** «SOAP — протокол: правила внутри сообщения (конверт, WSDL, WS-*). REST — стиль поверх HTTP: правила в методах и статусах, надёжность добавляем сами. SOAP берут, когда нужна формальная валидация и протокольная надёжность "из коробки" — банки, АБС, госсектор. Во всём остальном — REST. SOAP я умею читать: конверт, WSDL, где auth, где данные. Проектировать с нуля — не нужно.»

### 3.3 gRPC

Бинарный протокол, HTTP/2, контракт в protobuf:

```protobuf
// order.proto
syntax = "proto3";
package orders;

service OrderService {
  rpc CreateOrder (CreateOrderRequest) returns (Order);
  rpc GetOrder (GetOrderRequest) returns (Order);
}

message CreateOrderRequest {
  int64 user_id = 1;
  repeated OrderItem items = 2;
  int64 total_cents = 3;   // деньги в копейках, не float!
}

message OrderItem {
  string sku = 1;
  int32 qty = 2;
}

message Order {
  int64 order_id = 1;
  string status = 2;   // "CREATED", "PAID", "CANCELLED"
  int64 created_at = 3; // unix timestamp
}
```

Когда: внутренние микросервисы, высокая нагрузка, нужен стриминг. Не для внешнего API.

## 4. Асинхронные интеграции

### 4.1. Point-to-point vs Pub/Sub

**P2P (очередь, RabbitMQ):**
```
Продюсер ──> [очередь "emails"] ──> Воркер 1 (отправляет письмо)
Продюсер ──> [очередь "emails"] ──> Воркер 2 (если 1 занят)
```
Одно сообщение — одному воркеру. Забрали — исчезло.

**Pub/Sub (Kafka):**
```
Продюсер ──> [топик "orders"]
                 ├──> Сервис лояльности (consumer group A)
                 ├──> Сервис аналитики (consumer group B)
                 └──> Сервис push (consumer group C)
```
Одно событие — всем подписчикам. Событие **сохраняется** в топике.

### 4.2. Формат события (Kafka)

Сообщение в Kafka — это `key` + `value` + `headers`:

```
Key:   "order-123"          (для партиционирования: все события по заказу 123 в одну партицию)
Value:
{
  "eventId": "evt-abc-123",
  "eventType": "order.paid",
  "timestamp": "2026-09-20T19:00:01Z",
  "data": {
    "orderId": 123,
    "userId": 7,
    "amount": 500000,
    "paymentMethod": "CARD"
  }
}
Headers:
  correlationId: "req-xyz-789"
  sourceSystem: "order-service"
```

**Идемпотентность потребителя** — по `eventId`:
```
Сервис лояльности получает:
  { "eventId": "evt-abc-123", "data": { "orderId": 123, ... } }

SELECT processed FROM loyalty_events WHERE event_id = 'evt-abc-123';
  → если есть: ACK, ничего не делаем
  → если нет: начислить баллы, INSERT INTO loyalty_events (event_id, ...)
```

### 4.3. Kafka vs RabbitMQ

| | RabbitMQ | Kafka |
|---|---|---|
| Модель | Очередь (достал и забыл) | Журнал (сохраняется, можно перечитать) |
| Хранение | Пока не обработано | N дней/GB (настраивается) |
| Повторное чтение | Нет | Да (offset) |
| Параллелизм | Queue → N consumers (round-robin) | Topic → N partitions → N consumers |
| Когда | Задачи, письма, биллинг | События, аналитика, many subscribers |

## 5. Файловые интеграции и ETL

### 5.1. Файл по SFTP

Пример CSV-файла выгрузки остатков:
```
sku,warehouse_id,qty,updated_at
SKU-42,MSC-1,15,2026-09-20T03:00:00Z
SKU-43,MSC-1,0,2026-09-20T03:00:00Z
SKU-44,MSC-2,42,2026-09-20T03:00:00Z
... (2 000 000 строк)
```

**3 грабли:**

| Проблема | Пример | Решение |
|---|---|---|
| Файл-половинка | Запись оборвалась на строке 800 000 из 2 000 000 | Писать `file.tmp` → `file.csv` (atomic rename) |
| Дубль при повторе | Импортировали, не пометили, повторили | Идемпотентный импорт по `sku` + таблица `processed_files (hash, date)` |
| Смена схемы | Добавили колонку `price` после `qty` | Валидация шапки: если колонки не совпадают со схемой — алерт, не импортировать |

### 5.2. ETL

```
[1С БУХ] ──Extract──> [Staging DB] ──Transform──> [ДМ (отчётная БД)]
[CRM]     ──Extract──>    ↑               Load
[ERP]     ──Extract──>    │
[Excel]   ──Extract──>    │
                          └──> [Отчёт для бухгалтерии]
```

Аналитик описывает:
- источники (какие системы, какие таблицы/файлы)
- периодичность (раз в ночь, раз в месяц)
- маппинг полей (как поле `sum` из 1С становится `amount_cents` в ДМ)
- что при ошибке (скипнуть строку? остановить загрузку?)
- как проверить результат (сверка сумм, количество строк)

## 6. Сравнительная таблица и чек-лист

| Тип | Ответ сейчас? | Объём | Надёжность | Сложность | Где |
|---|---|---|---|---|---|
| REST | Да | малый/средний | средняя (retry) | низкая | большинство API |
| SOAP | Да | средний | высокая (WS-*) | средняя | банки, АБС |
| gRPC | Да | малый, частый | средняя | средняя | внутренние микросервисы |
| RabbitMQ | Нет | средний | высокая | средняя | задачи, письма |
| Kafka | Нет | большой, поток | высокая | высокая | события, аналитика |
| Файл/SFTP | Нет (расписание) | большой | средняя | низкая | отчёты, 1С, B2B |
| ETL | Нет (пакет) | очень большой | средняя | средняя | ДМ, отчётность |

### Чек-лист выбора (6 вопросов)

1. **Нужен ответ «прямо сейчас»?** Да → синхронная. Нет → можно асинхронная.
2. **Что будет, если вторая система упала?**
   - нельзя потерять → синхронная с retry / асинхронная с гарантированной доставкой
   - можно позже → файл, событие без SLA
3. **Сколько данных и с какой частотой?**
   - много + поток → Kafka
   - много + раз в день → файл/ETL
   - по чуть-чуть часто → REST
4. **Кто вторая сторона?**
   - банк/АБС/gov → SOAP (или файл)
   - наш сервис → REST (или gRPC)
   - партнёр без API → файл
5. **Сколько потребителей?**
   - один → p2p или REST
   - много + история → Kafka
6. **Есть ли требование к формату у второй стороны?** (банк → XML/SOAP, партнёр → CSV)

**Формула ответа на собесе:**
«Я бы выбрал(а) **X**, потому что [контекст]. Альтернатива — **Y**, она была бы лучше, если [условие]. Минусы X — [честно].»

## 7. Практика: 6 кейсов

Для каждого: (1) тип, (2) почему, (3) альтернатива + когда она лучше.

| # | Кейс | Ожидаемый ответ |
|---|---|---|
| 1 | Оплата картой, ответ до закрытия вкладки | Синхронная (REST/SOAP). Alt: async, если бизнес допускает задержку |
| 2 | После оплаты: баллы + статистика + push | Async pub/sub (Kafka). Alt: 3 REST-вызова, если объём малый |
| 3 | 2 млн строк остатков раз в ночь | Файл SFTP / ETL. Alt: REST с пагинацией, если <100k |
| 4 | АБС банка, «как у всех банков» | SOAP + XML. Alt: REST, если банк модернизился |
| 5 | Микросервисы, изменение остатка, высокая нагрузка, ответ не нужен | Kafka (событие). Alt: gRPC, если нужен sync |
| 6 | Отчёт для бухгалтера, 12 источников, раз в месяц | ETL. Alt: 12 REST + скрипт, если объёмы малые |

## 8. Как аналитик описывает интеграцию в ТЗ (10 пунктов)

Пример записи в ТЗ для интеграции «Создание заказа»:

```
ИНТЕГРАЦИЯ: Создание заказа (OrderService → PaymentService)
```

## Резюме занятия

- Интеграция = обмен между системами. На границе — 80% проблем.
- Первое разделение: **синхронное** (ждём ответ) vs **асинхронное** (положили и поехали).
- Синхронные: REST (основа), SOAP (читать, банки), gRPC (внутри, скорость).
- Асинхронные: очередь p2p (задачи), Kafka (события, многим, история).
- Идемпотентность потребителя: проверить `eventId`, не обрабатывать дубли.
- Файл/ETL: 3 грабли (половинка, дубль, смена схемы).
- Выбор = чек-лист: ответ сейчас? упала система? объём? кто вторая сторона? сколько потребителей?
- В ТЗ: 10 пунктов. Джуны забывают: retry, идемпотентность, SLA.
