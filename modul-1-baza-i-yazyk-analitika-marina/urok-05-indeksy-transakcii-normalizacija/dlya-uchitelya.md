## 4. Сценарий по шагам
### 4.1. Вступление (3 мин)
Объявить: «Сегодня разбираем три темы, которые влияют на **производительность и структуру** данных. Это знания, которые вы будете использовать в требованиях каждый день».
### 4.2. Индексы (15 мин)

**Определение (показать дословно):**
> Индекс в БД — как алфавитный указатель в книге. Позволяет находить данные быстро, не сканируя всю таблицу.

Показать до/после:
```sql
-- Без индекса: БД проходит ВСЕ строки
SELECT * FROM users WHERE email = 'anna@mail.ru';

-- С индексом: БД идёт сразу к нужной записи
CREATE INDEX idx_users_email ON users(email);
SELECT * FROM users WHERE email = 'anna@mail.ru';
```

**B-дерево** — объяснить на аналогии словаря: буква → страница → слово. Для 1000 записей — 3–4 уровня. Скорость не зависит от объёма таблицы.

**Важные акценты для аналитика:**
- Аналитик формулирует требования: «поиск по email должен работать за 100мс». Это требование → индекс.
- Индекс = компромисс: быстрое чтение, медленная запись. Если таблица часто обновляется — лишние индексы тормозят запись.
- Колонка для индекса: **высокая селективность** (много уникальных значений, например email, id). Не стоит индексировать колонку «пол» (0/1) — БД не сможет отсечь половину данных.

**Когда индекс помогает:**
- WHERE по индекс-колонке
- JOIN по индекс-колонке
- ORDER BY по индекс-колонке

**Когда мешает:**
- Вставка/обновление каждой строки (нужно обновлять индекс)
- Маленькая таблица (нет смысла)
- Колонка с низкой селективностью
### 4.3. UNIQUE-индекс (5 мин)
Показать:
```sql
ALTER TABLE users ADD CONSTRAINT uq_users_email UNIQUE (email);
```

Попытка вставить дубликат → ошибка.

Для аналитика: требование «каждый email должен быть уникальным» → UNIQUE-индекс. Это и защита данных, и ускорение поиска.
### 4.4. Транзакции и ACID (10 мин)

**Определение:**
> Транзакция — набор операций, которые выполняются все сразу или ни одна.

Аналогия: банковский перевод — списание и зачисление должны произойти вместе. Если одна упала — откатываем обе.

Показать пример:
```sql
BEGIN;
UPDATE accounts SET balance = balance - 5000 WHERE id = 1;
UPDATE accounts SET balance = balance + 5000 WHERE id = 2;
COMMIT;
```

**ACID — разобрать каждое свойство:**

1. **Атомарность (Atomicity):** «Всё или ничего». Если вторая команда упала — откатываем первую.
2. **Согласованность (Consistency):** После транзакции данные «корректны» (баланс не ушёл в минус, если это запрещено).
3. **Изоляция (Isolation):** Параллельные транзакции не мешают друг другу. (Не углубляться в уровни изоляции.)
4. **Долговечность (Durability):** После COMMIT данные сохраняются, даже если сервер упал.

Для аналитика: требование «перевод должен быть атомарным» → транзакция. Это влияет на проектирование API и БД.
### 4.5. COMMIT и ROLLBACK (5 мин)
Показать пример:
```sql
BEGIN;
UPDATE accounts SET balance = balance - 10000 WHERE id = 1;
-- Ошибка: баланс стал отрицательным
ROLLBACK;
-- Баланс вернулся к исходному
```

Без BEGIN/COMMIT каждая команда — отдельная транзакция (auto-commit). Это опасно для составных операций.
### 4.6. Нормализация (10 мин)

**Зачем:** чтобы не было дублирования, обновление данных не ломало другие данные.

**1НФ — нет повторяющихся групп:**
Показать «до/после»:
- До: user_id | orders: "З1, З2, З3" (одна ячейка — много значений)
- После: отдельные строки для каждого заказа

Правило: в каждой ячейке — одно значение.

**2НФ — нет зависимостей от части ключа:**
Показать: order_items с product_name внутри. product_name зависит от product_id, не от всего ключа. Выносим в таблицу products.

Правило: если данные зависят не от всего первичного ключа, а от его части — выноси в отдельную таблицу.

**3НФ — нет транзитивных зависимостей:**
Показать: user → city → city_name. city_name зависит от city_id, не от user_id. Выносим в таблицу cities.

Правило: если данные зависят от «посредника» (не от ключа напрямую) — выноси.
### 4.7. Денормализация (5 мин)
Объяснить: нормализация — это хорошо для данных, но иногда **read-only запросы** (отчёты) работают медленно с джойнами 5 таблиц. Денормализация = намеренно дублируем данные для скорости.

Пример: `total_price` в заказе (хотя можно посчитать через order_items).

Для аналитика: понимать, что «красивая структура ≠ быстрая». Требования к скорости определяют баланс.
### 4.8. Практика 1 (10 мин)
Задания:
1. Создать индекс по `orders.user_id`
2. Запустить `EXPLAIN SELECT * FROM orders WHERE user_id = 1`
3. Сравнить с EXPLAIN до индекса

**Ожидаемый результат EXPLAIN:**
- Без индекса: `Seq Scan on orders` (полное сканирование)
- С индексом: `Index Scan using idx_orders_user_id on orders` (быстрый поиск)

## 6. Типичные ошибки и как реагировать

| Ошибка | Реакция учителя |
|---|---|
| «Индекс = первичный ключ» | Уточнить: PK — это индекс, но индекс ≠ PK; индексов может быть много |
| «ACID = база данных» | Уточнить: ACID — свойства транзакций, а не самой БД |
| Путает 2НФ и 3НФ | 2НФ = зависимости от части ключа; 3НФ = транзитивные зависимости |
| Не видит разницы между BEGIN и auto-commit | Показать: BEGIN + 2 запроса + COMMIT = одна «единица»; без BEGIN — две отдельные |
| Денормализация = плохо | Объяснить: это компромисс, оправданный для read-heavy систем |

## 10. Заметки по проведению

- Индексы — тема, где ученик может «зацепиться» на B-дереве. Если путается — вернуться к аналогии со словарём.
- ACID: не углубляться в уровни изоляции — это advanced-тема. Достаточно понимания «всё или ничего».
- Нормализация: показывать «до/после» на конкретных таблицах. Абстрактные объяснения не работают.
- Денормализация: подчеркнуть, что аналитик иногда **требует** denormalized данные для отчётов — это осознанный выбор.
