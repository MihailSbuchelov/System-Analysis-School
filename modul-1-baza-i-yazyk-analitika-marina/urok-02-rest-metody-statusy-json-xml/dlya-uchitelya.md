# Урок 2. Текст для учителя

**REST: методы, статусы, JSON/XML; практика в Postman и curl**
Модуль 1, урок 2 · 90 минут · уровень: джун-мидл → аналитик

---

## 1. Цели урока

После урока ученик умеет:

- объяснить, что такое API и почему аналитик описывает его в требованиях;
- сказать своими словами, что REST — это архитектурный стиль, а не протокол;
- назвать пять HTTP-методов (GET, POST, PUT, PATCH, DELETE), их смысл и отличия;
- различать идемпотентные и неидемпотентные методы (простыми словами);
- пользоваться группами статус-кодов 2xx/3xx/4xx/5xx и приводить примеры 200, 201, 204, 400, 401, 403, 404, 500, 502;
- читать JSON и базово — XML, назвать плюсы JSON для современных API;
- выполнить GET/POST/PUT/DELETE в Postman и curl к публичному API и объяснить ответ.

**Не цель урока:** проектировать API, разбирать тонкости HTTP-стандарта, глубоко вникать в SOAP/WSDL, писать код сервисов. Это будет в модуле 3 (интеграции).

## 3. Подготовка к уроку

- Проверить заранее, что `jsonplaceholder.typicode.com` доступен у ученика (это «тестовый» публичный API, который всегда отдаёт демо-данные).
- Установить/проверить Postman (desktop или браузерная версия) или запасной вариант — только curl в PowerShell.
- Убедиться, что у ученика Windows 10+ (там встроен `curl.exe`); проверить отдельно: `curl --version`.
- Подготовить скриншоты ответов Postman на случай, если сеть недоступна.
- Повторить RFC: разница POST/PUT, смысл 401 vs 403, 500 vs 502 — чтобы отвечать без запинки.

## 4. Сценарий по шагам

### 4.1. Вступление (3–5 мин)
Опорная фраза: «В уроке 1 мы научились видеть, что сервер и клиент общаются по HTTP. Сегодня разберём правила этого общения, которые использует почти любой современный сервис». Объявить, что итог урока — ученик сам сделает 4 типа запросов в двух инструментах.

### 4.2. API и зачем это аналитику (слайд 2)

Определение для записи:

> API — правила, по которым одна программа общается с другой.

Проговорить аналогию «меню ресторана»: гость (клиент) выбирает блюдо из меню, официант приносит то, что приготовлено; на кухню (внутренности) не пускают. Для аналитика важно: API — это **договор между системами**. В требованиях аналитик пишет не «система А позвонит системе Б», а именно правила: какие адреса, какие данные, какие ответы.

Акцент: аналитику не обязательно писать код API, но читать его описание и понимать «кто что кому отдаёт» — обязательно.

### 4.3. REST — архитектурный стиль (слайд 3)
Повторить, что HTTP — протокол, а REST — **стиль** (набор идей), который на HTTP строится. Аналогия: HTTP — это «русский язык», REST — «как правильно разговаривать по-русски в деловой переписке».

Обязательно упомянуть: REST и SOAP — **разные парадигмы**, «REST не реализует SOAP». SOAP — строгий протокол, данные только в XML, много служебных обёрток; REST — простые HTTP-запросы и JSON. Сейчас в новых проектах REST (или более новые стили GraphQL/gRPC) — норма, SOAP — редкость (обычно в legacy-банках/гос-системах).

### 4.4. Ресурсы и URI (слайд 4)
Показать формулу `URI = /сущность/идентификатор`. Разобрать примеры, спросить ученика: «как на ваш взгляд выглядел бы адрес каталога товаров?» Обратить внимание на то, что плохие имена URI обходятся дорого — потом их сложно менять, «это решение в требованиях».

### 4.5. Методы (слайд 5)
Пройти таблицу методов построчно, каждый с примером из магазина. Подчеркнуть пару GET (читать) / POST (создавать) — это минимум, без которого не бывает ни одного REST API. PUT — «заменить целиком», PATCH — «подправить чуть-чуть». Демонстрация: показать в Postman текст запроса и переключить метод.

### 4.6. Идемпотентность (слайд 6)
Дать простое определение и таблицу. Обязательно нарисовать sequence-диаграмму двойного POST (два заказа!). Спросить: «где вы в реальной жизни видели такое?» — ответ «перепроверьте, не двойной ли заказ» (защита от повторной отправки формы). Именно так это и звучит в требованиях, и это слово — «идемпотентность» — ученик должен запомнить.

### 4.7. Статусы (слайды 7–8)
Объяснить «мнемонику»: 4xx — вина того, кто спросил, 5xx — вина того, кто отвечает. Разобрать 200, 201, 204, 400, 401, 403, 404, 500, 502 с бытовыми примерами:
- 401 — «предъявите пропуск»;
- 403 — «пропуск есть, но в этот кабинет вход запрещён»;
- 502 — «охрана не дозвонилась до директора» (прокси не достучался до бэкенда);
- 204 — «удалите — и тишина».

Акцент для аналитика: аналитик должен **проектировать статусы** в требованиях (например, «если товара нет, вернуть 404»), потому что это влияет на поведение других систем.

### 4.8. JSON и XML (слайды 9–10)
Сначала показать JSON, разобрать «ключ: значение». Спросить: «почему у name кавычки есть, а у 120000 нет?» (строка vs число). Потом тот же объект в XML и составить сравнительную таблицу. Вывод: современный REST — JSON; XML — для SOAP и legacy.

### 4.9. Полный цикл запроса (слайд 11)
Прогнать sequence-диаграмму вслух: «клиент vs создаёт пользователя → сервер вставляет строку в БД → отвечает 201. Дальше читаем того же пользователя → 200». Подчеркнуть, что статус приходит от сервера, а тело — «доказательство выполненной работы».

### 4.10. Практика 1 (10 мин)
Разобрать экран Postman: поле адреса, выпадающий список методов, кнопка Send, панель Response со статусом, телом и заголовками. Ученик делает первый GET и отвечает на 3 вопроса слайда. Роль учителя — наблюдать, поправлять адрес (ошибки «очепятки» в URI).

### 4.11. Практика 2 (15 мин)
Ученик проходит таблицу из 5 запросов. Задача-ловушка: при `POST /posts` сервер отвечает **201**, а при повторном POST — снова 201 и новый id. Обсудить: «сервер честно создаёт каждый раз. Как защититься на стороне клиента?» — «не дублировать клики, дать пользователю понятную ошибку».

### 4.12. Практика 3 (10 мин)
Те же запросы в curl. Помочь: в PowerShell кавычки и `^` аккуратно; показать, что `-X POST` + `-d` создаёт тело с заголовком Content-Type. Альтернатива, если что-то не идёт: `curl -i` — показать строку статуса.

### 4.13. Ревью (13 мин)
Собрать таблицу «запрос → полученный статус» у всей группы. Проговорить вопросы слайда «Ревью»:
- POST → 201, PUT → 200 (тело изменённого ресурса) — почему не один и тот же?
- повторный GET ничего не меняет, повторный POST — меняет (идемпотентность).
- DELETE несуществующего — по-разному: 404 «не нашли» или 204 «и так нет»; в требованиях это надо явно прописывать.

### 4.14. Домашнее задание и завершение (7 мин)
Разобрать формулировки ДЗ. Дать подсказку к вопросу №4: 201 звучит как «создали!», 200 — «всё ок, вот результат»; для «создали, но возвращать нечего» есть 204.

## 6. Типичные ошибки и как реагировать

| Ошибка | Реакция учителя |
|---|---|
| «REST — это протокол» | Вернуть к аналогии «язык vs стиль общения»; HTTP — протокол, REST — идеи на нём |
| Путает PUT и PATCH | Пример: PATCH меняет цену, PUT перезаписывает товар целиком |
| «GET можно что-то создать» | Показать, что GET не имеет тела и «не должен менять состояние» |
| Путает 401 и 403 | Развести: нет данных для входа (401) vs получил доступ, но прав нет (403) |
| Путает 500 и 502 | 500 — упал сам сервер; 502 — упал «посредник» при запросе к бэкенду |
| «Статус 200 бывает всегда» | Показать 201/204/404 на практике — статусы разные под разные действия |
| Забывает кавычки в JSON-строках | Вернуть к слайду JSON: строки — двойные кавычки, числа — без |
| Повторный POST «сомневается» | Напомнить идемпотентность: POST не идемпотентен, сервер создаёт новое |

## 8. Домашнее задание — разбор и ответы

1. **10 запросов магазина** (пример): GET /products, GET /products/5, GET /search?q=phone, POST /cart, GET /cart, PATCH /cart/5 (поменять количество), DELETE /cart/5, POST /orders, GET /orders/123, GET /users/me. Каждый — с ожидаемым статусом (200/201/204 и т.п.).
2. **По одному запросу каждого метода** (пример результата): GET /posts/1 → 200, POST /posts → 201, PUT /posts/1 → 200, PATCH /posts/1 → 200, DELETE /posts/1 → 200. Скриншоты строк состояния.
3. **Примеры из GitHub API** (по документации docs.github.com): GET /users/{username} → 200, POST /repos → 201, DELETE /repos/{owner}/{repo} → 204. Для каждого — «что делает, что вернёт».
4. **201 vs 200 vs 204**: 201 — «создали и показываем id», 200 — «обычный успех с данными», 204 — «успех без тела». Ответ на вопрос: 204 (пустое тело после DELETE/POST без возврата).

## 10. Заметки по проведению

- Слабое место «сильных» учеников — спешка «сделать запрос» без осознания, какой статус и почему. Каждый запрос просим сопровождать «словами аналитика»: что попросили и что получили.
- Если ученик пользуется браузером вместо Postman — допустимо, но именно Postman даёт наглядную строку статуса и удобный разбор.
- Хорошо работает вопрос-якорь «где здесь двойной заказ?» — он «приклеивает» идемпотентность к реальному бизнесу.
- Держите скриншоты Postman наготове: если у ученика проблемы с сетью, практику можно «сыграть» на скриншотах и обсудить статусы.
